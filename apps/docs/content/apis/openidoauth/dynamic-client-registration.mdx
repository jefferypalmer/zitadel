ZITADEL implements OAuth 2.0 Dynamic Client Registration so that AI agent
tooling, MCP servers, and any RFC 7591 client provisioner can register OAuth
clients without operator intervention. This page is the API reference;
operational decisions (anonymous-by-default, T16 rotating-IP residual risk,
audit shape) live in [SECURITY.md](https://github.com/zitadel/zitadel/blob/main/SECURITY.md)
and [ADR-0001](https://github.com/zitadel/zitadel/blob/main/docs/adr/ADR-0001-dynamic-client-registration.md).

**Specs implemented**

| RFC / spec                                                                                                      | What ZITADEL conforms to                                                                         |
| --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| [RFC 7591](https://datatracker.ietf.org/doc/html/rfc7591)                                                       | Dynamic Client Registration Protocol (POST /register, error envelope, metadata fields).          |
| [RFC 7592](https://datatracker.ietf.org/doc/html/rfc7592)                                                       | Dynamic Client Registration Management Protocol (GET / PUT / DELETE on `/register/{client_id}`). |
| [RFC 8414](https://datatracker.ietf.org/doc/html/rfc8414)                                                       | OAuth 2.0 Authorization Server Metadata (`/.well-known/oauth-authorization-server`).             |
| [RFC 8707](https://datatracker.ietf.org/doc/html/rfc8707)                                                       | Resource Indicators — `resource` parameter on `/authorize` and `/token`.                         |
| [RFC 8252](https://datatracker.ietf.org/doc/html/rfc8252)                                                       | OAuth 2.0 for Native Apps (loopback redirect URI guidance).                                      |
| [RFC 9700](https://datatracker.ietf.org/doc/html/rfc9700)                                                       | Best Current Practice for OAuth 2.0 Security.                                                    |
| [OpenID Connect Dynamic Client Registration 1.0](https://openid.net/specs/openid-connect-registration-1_0.html) | OIDC additions to the metadata model.                                                            |

ZITADEL ships DCR **disabled by default**. Enable it by flipping
`OIDC.DCR.Enabled: true` in `defaults.yaml` AND turning on the
`dynamic_client_registration` instance feature flag.

## Endpoints

| Method | Path                                            | Purpose                                                                      |
| ------ | ----------------------------------------------- | ---------------------------------------------------------------------------- |
| POST   | `${CUSTOM_DOMAIN}/oidc/v1/register`             | Register a new client. RFC 7591 §3.1.                                        |
| GET    | `${CUSTOM_DOMAIN}/oidc/v1/register/{client_id}` | Read a registered client. RFC 7592 §2.1.                                     |
| PUT    | `${CUSTOM_DOMAIN}/oidc/v1/register/{client_id}` | Update a registered client. RFC 7592 §2.2.                                   |
| DELETE | `${CUSTOM_DOMAIN}/oidc/v1/register/{client_id}` | Delete a registered client and revoke its outstanding tokens. RFC 7592 §2.3. |

When DCR is disabled, every endpoint above returns `404 Not Found` and the
`registration_endpoint` field is **omitted** from the discovery and AS metadata
documents (the field is never emitted as `null`). When DCR is enabled but the
runtime feature flag is off, the endpoints return `403` with
`error: feature_disabled`.

### Discovery + RFC 8414

The `registration_endpoint` is advertised in two places, with byte-identical
values when DCR is enabled:

- `${CUSTOM_DOMAIN}/.well-known/openid-configuration` (existing OIDC discovery).
- `${CUSTOM_DOMAIN}/.well-known/oauth-authorization-server` (RFC 8414).

Sample (DCR enabled):

```json
{
  "issuer": "https://example.zitadel.cloud",
  "authorization_endpoint": "https://example.zitadel.cloud/oauth/v2/authorize",
  "token_endpoint": "https://example.zitadel.cloud/oauth/v2/token",
  "registration_endpoint": "https://example.zitadel.cloud/oidc/v1/register",
  "jwks_uri": "https://example.zitadel.cloud/oauth/v2/keys"
}
```

Sample (DCR disabled — note the absence of `registration_endpoint`):

```json
{
  "issuer": "https://example.zitadel.cloud",
  "authorization_endpoint": "https://example.zitadel.cloud/oauth/v2/authorize",
  "token_endpoint": "https://example.zitadel.cloud/oauth/v2/token",
  "jwks_uri": "https://example.zitadel.cloud/oauth/v2/keys"
}
```

### Hostname-root deployment requirement

DCR is only supported on **hostname-root** issuer URLs (`https://example.com/`),
not on subpath issuers (`https://example.com/zitadel/`). MCP clients including
Claude Code resolve `registration_endpoint` against the issuer host, not the
issuer path. ZITADEL emits a warning to its structured log on the first
request to `/.well-known/oauth-authorization-server` from a subpath issuer
(deduplicated per `(instance, issuer)` tuple), naming the probed URL —
treat that warning as a deployment defect and fix it before exposing DCR
to MCP-style consumers.

## Authentication modes

DCR supports two registration modes. The mode is set by the operator via
`OIDC.DCR.RequireInitialAccessToken`.

### Anonymous mode (default)

`POST /oidc/v1/register` accepts requests without an `Authorization` header.
The endpoint hardens itself in place of authentication:

- per-instance access quota inherited from the existing rate-limiting
  middleware,
- mandatory `redirect_uris` clamping through the OIDC compliance rules and
  the operator-configured `AllowedRedirectURIHostPatterns` allow-list,
- mandatory PKCE S256 when `token_endpoint_auth_method=none`,
- `MaxRequestBodyBytes` cap (default 64 KiB),
- audit log row on every registration carrying source-IP SHA-256 + User-Agent.

This mode is what Claude Code, MCP Inspector, and `mcp-remote` expect.

### Initial Access Token (IAT) mode

When `OIDC.DCR.RequireInitialAccessToken: true` is set, an instance admin
mints an Initial Access Token via the admin gRPC API and provides it to the
provisioning system. The token must be presented as a `Bearer` token on the
`Authorization` header.

```http
POST /oidc/v1/register HTTP/1.1
Host: example.zitadel.cloud
Content-Type: application/json
Authorization: Bearer zdiat_<id>.<random>
```

IAT-mode is incompatible with Claude Code today — Claude Code cannot supply
an Initial Access Token. Operators that flip this mode accept that
trade-off explicitly.

IAT semantics:

- Each IAT carries `{instance_id, org_id, project_id}` claims; the registered
  client lands in that project, regardless of where the request originated.
- `max_uses` enforces a registration cap with eventstore-level uniqueness;
  the value `0` means unlimited.
- Lifetime is enforced server-side; expired or revoked IATs return
  `401 invalid_token`.
- Cross-instance / cross-org IAT abuse is rejected with the same anti-
  enumeration timing-equivalent response.

## Request — register a new client

The request body is a JSON object with the RFC 7591 metadata fields. ZITADEL
clamps every metadata field against operator-configured allow-lists; the
response echoes the clamped values (RFC 7591 §3.2.1).

### Metadata fields

| Field                                                                                                                                                                                                                    | Type              | Notes                                                                                                                                                                                                                                                               |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `client_name`                                                                                                                                                                                                            | string            | Free text, displayed in audit + console. Empty value is replaced with the minted `client_id` post-registration.                                                                                                                                                     |
| `redirect_uris`                                                                                                                                                                                                          | string[]          | Required. Must satisfy the OIDC v1 compliance rules + `OIDC.DCR.AllowedRedirectURIHostPatterns` regex if configured. | `grant_types`                                                                                                                                                                                                            | string[]          | Default `["authorization_code"]`. Server intersects with `OIDC.DCR.AllowedGrantTypes`.                                                                                                                                                                              |
| `response_types`                                                                                                                                                                                                         | string[]          | Default `["code"]`. Server intersects with `OIDC.DCR.AllowedResponseTypes`.                                                                                                                                                                                         |
| `token_endpoint_auth_method`                                                                                                                                                                                             | string            | Default `client_secret_basic`. Allowed: `none`, `client_secret_basic`, `client_secret_post`, `private_key_jwt`. `client_secret_jwt` is rejected with `invalid_client_metadata`.                                                                                     |

| `software_statement`                                                                                                                                                                                                     | JWT               | Rejected with `unapproved_software_statement` unless `OIDC.DCR.SoftwareStatement.Enabled: true`.                                                                                                                                                                    |

### Status code matrix

| Status | Error code                      | When                                                                             |
| ------ | ------------------------------- | -------------------------------------------------------------------------------- |
| 201    | —                               | Registration succeeded.                                                          |
| 400    | `invalid_client_metadata`       | Schema/JSON failure or clamp produced an empty intersection on a required field. |
| 400    | `invalid_redirect_uri`          | Any `redirect_uri` failed compliance or host-pattern validation.                 |
| 400    | `invalid_software_statement`    | Statement supplied while feature on, but content is malformed/untrusted.         |
| 400    | `unapproved_software_statement` | Statement supplied while feature off.                                            |
| 401    | `invalid_token`                 | IAT mode: missing / invalid / expired / revoked / exhausted IAT.                 |
| 403    | `feature_disabled`              | DCR yaml on, instance feature flag off.                                          |
| 404    | —                               | DCR yaml off; the endpoint is unmounted.                                         |
| 413    | `payload_too_large`             | Body > `MaxRequestBodyBytes`.                                                    |
| 415    | `unsupported_media_type`        | `Content-Type` not `application/json`.                                           |
| 429    | —                               | Instance rate limit.                                                             |

### Response — 201 body

A successful registration returns 201 with `Cache-Control: no-store` and
`Pragma: no-cache`. The body echoes the clamped metadata plus:

- `client_id` (server-generated),
- `client_secret` (only when the auth method is `client_secret_basic` or
  `client_secret_post` — emitted exactly once, never retrievable later),
- `client_id_issued_at` (Unix seconds),
- `client_secret_expires_at` (Unix seconds; `0` means no expiry — RFC 7591
  §3.2.1),
- `registration_access_token` (RAT plaintext — emitted exactly once,
  required for RFC 7592 management),
- `registration_client_uri` (the URL of the management endpoint for this
  client).

### Anonymous-mode example

```bash
curl -sS -X POST 'https://example.zitadel.cloud/oidc/v1/register' \
  -H 'Content-Type: application/json' \
  -d '{
    "client_name": "demo-cli",
    "redirect_uris": ["https://demo.example.com/cb"],
    "grant_types": ["authorization_code"],
    "response_types": ["code"],
    "token_endpoint_auth_method": "client_secret_basic",
    "application_type": "web"
  }'
```

### IAT-mode example

```bash
curl -sS -X POST 'https://example.zitadel.cloud/oidc/v1/register' \
  -H 'Content-Type: application/json' \
  -H "Authorization: Bearer ${IAT}" \
  -d '{
    "client_name": "provisioned-tool",
    "redirect_uris": ["https://provisioner.example.com/cb"],
    "grant_types": ["authorization_code", "refresh_token"],
    "token_endpoint_auth_method": "client_secret_post",
    "application_type": "web"
  }'
```

## Manage a registered client (RFC 7592)

Every successful registration returns a `registration_access_token` (RAT)
that authenticates GET / PUT / DELETE on `/oidc/v1/register/{client_id}`.
The RAT is hashed at rest with Passwap and rotated on every successful
PUT (stricter than RFC 7592's MAY).

### Anti-enumeration contract

Unknown `client_id`, wrong RAT, and expired RAT all collapse to a single
`401 invalid_token` response with the `WWW-Authenticate: Bearer error="invalid_token"`
header. Both branches (known-client / unknown-client) run a real Passwap
`Verify` against the stored hash or a precomputed startup-time dummy hash
respectively, so the response time is timing-equivalent.

### PUT idempotency caveat

Because PUT rotates the RAT atomically, the operation is **not idempotent**
in the HTTP sense — a retried PUT with the previous (rotated) RAT will
return 401. Provisioning systems must persist the freshly-issued RAT from
the PUT 200 response BEFORE attempting any retry.

### DELETE — token revocation

`DELETE /oidc/v1/register/{client_id}` returns 204 and revokes the client's
outstanding access and refresh tokens on the same transaction.

## Security guarantees

### `jwks_uri` SSRF defence

When a registration sets `token_endpoint_auth_method=private_key_jwt` and
includes a `jwks_uri`, ZITADEL fetches that URL during validation. The
fetcher enforces:

- IP deny-list (RFC 1918, loopback, link-local, IPv6 ULA — operator-tunable
  via `OIDC.DCR.JwksURI.DisallowedIPRanges`);
- DNS-rebind defence (single-resolve per hop + pinned-IP dial);
- 3-hop redirect cap with per-hop re-validation of the resolved IP;
- 1 MiB body cap;
- `OIDC.DCR.JwksURI.HTTPTimeout` (default 10s);
- `OIDC.DCR.JwksURI.AllowLoopbackInDev` lifts the loopback ban for local
  development only.

### Rate limiting

DCR endpoints are wrapped by ZITADEL's existing per-instance access quota
middleware. Operators that disable IAT mode and expose DCR to the public
internet must size the quota for the expected registration volume. For
distributed-IP-flood defence (T16 in the threat model), front the
endpoint with a CDN or WAF capable of distributed-IP rate-limiting; the
ZITADEL instance quota alone cannot defend against a botnet that
distributes one request per source IP. See
[ADR-0001 §T16](https://github.com/zitadel/zitadel/blob/main/docs/adr/ADR-0001-dynamic-client-registration.md)
for the product sign-off on this residual risk.

### Audit log

Every successful registration emits a
`project.application.dynamically.registered` event on the project
aggregate carrying `{client_id, iat_id, software_statement_jti,
registration_method, client_name_unclamped, remote_addr_sha256,
user_agent}`. The remote-IP SHA-256 is derived from
`X-Forwarded-For` first hop, falling back to `r.RemoteAddr`. ZITADEL
deliberately does NOT parse `CF-Connecting-IP`, `X-Real-IP`, or
RFC 7239 `Forwarded` — operators terminating TLS in front of ZITADEL
must rewrite into `X-Forwarded-For` at the ingress.

### TLS posture

The DCR endpoints run inside the same HTTP server as `/oidc/v1/userinfo`
and inherit the same TLS posture. There are no DCR-specific TLS knobs.

## Observability

DCR emits OpenTelemetry spans and metrics under the `oidc.dcr.*` and
`zitadel.dcr.*` namespaces respectively. Phase 1 ships the registration
hot path counters; Phase 2 adds three counters covering org-policy churn,
software_statement verification, and the per-issuer JWKS cache.

### Metrics

| Metric | Type | Labels | Source |
|--------|------|--------|--------|
| `zitadel.dcr.registrations_total` | counter | `result`, `auth_method`, `application_type` | every `POST /oidc/v1/register` exit |
| `zitadel.dcr.request_duration_seconds` | histogram | — | every DCR HTTP request |
| `zitadel.dcr.errors_total` | counter | `code` (RFC 7591 error code) | every error envelope emitted |
| `zitadel.dcr.iat.consumed_total` | counter | — | every successful IAT slot consume |
| `zitadel.dcr.iat.exhausted_total` | counter | — | every IAT consume that fails because all slots are taken |
| `zitadel.dcr.org_policy_changes_total` | counter | `org_id`, `scope ∈ {org,instance}`, `result ∈ {accepted,rejected}` | every `OrgDCRPolicy*` / `InstanceDCRPolicy*` command exit |
| `zitadel.dcr.software_statement_verifications_total` | counter | `iss`, `result ∈ {accepted,untrusted,expired,replay,invalid_signature,invalid_structure,fetch_failed,unsupported_algorithm,missing_required_claim,not_yet_valid}` | every `software_statement` verifier exit |
| `zitadel.dcr.software_statement_jwks_cache_hits_total` | counter | `iss`, `outcome ∈ {hit,miss,refetch_failed}` | every per-issuer JWKS cache lookup |

Notes:

- `zitadel.dcr.org_policy_changes_total` carries `scope=instance` for
  the instance-default tier with `org_id="instance"` (label cardinality
  bound). Org commands carry `scope=org` with `org_id` set to the
  resource owner.
- `zitadel.dcr.software_statement_jwks_cache_hits_total` reports
  `outcome=refetch_failed` only when the cache previously held an
  entry for the issuer and the rotation refetch failed — fail-closed
  per RFC 7591 §2.3 (the verifier MUST NOT serve stale on rotation
  refetch failure).
- The Console UI does NOT introduce its own OTel spans or metrics.
  Operator panel actions hit the standard Management gRPC surface and
  surface inside the existing gRPC server-interceptor instrumentation.

### Span attributes

| Span | Attribute | Source | Notes |
|------|-----------|--------|-------|
| `oidc.dcr.register` | `dcr.policy.scope = org \| instance \| static-config` | merged DCR policy resolution at register time | Reports the tier the per-(instance, org) merge resolved against. The org allow-list URI list itself is NEVER an attribute. |
| `oidc.dcr.register`, `oidc.dcr.update` | `dcr.jwks.source = inline \| uri \| none` | clamped request body | `inline` when the body provided inline `jwks`; `uri` when only `jwks_uri` was provided; `none` when neither. The JWK Set content is NEVER an attribute. |
| `oidc.dcr.software_statement.verify` | `iss`, `result` | parsed `software_statement` body + verifier outcome | The raw JWT, raw timestamps, and JWKS payload are NEVER attributes — `iss` is RFC 7519 §4.1.1 identifier-only, non-secret. |

### Audit log events

`project.application.dynamically.registered` and
`project.application.registration_access_token.rotated` are the two
DCR-specific events on the project aggregate. The rotation event is
emitted on **both** operator-initiated rotation (Phase 2 console-side
"Rotate RAT" button) and client-initiated rotation (RFC 7592 PUT). Audit
consumers MUST NOT use the event type alone to distinguish operator
vs. client rotation — read the eventstore actor field on the event row
to disambiguate. The payload is identical in both cases.

`OrgDCRPolicy*` / `InstanceDCRPolicy*` commands also emit a redacted
INFO log on success and a WARN log on R4/R5 validation failure. The
INFO payload reports `instance_id, resource_owner, scope,
allowed_audiences_count` (an `int`, never the URI list) and the
lifetime; the WARN payload reports `instance_id, resource_owner,
error_key, first_violating_value` and never the full submitted list —
org allow-lists may name internal-only resources whose existence is
itself sensitive.

## Identifying DCR clients in the Management API

`GetApp`, `ListApps`, and the application-detail proto responses now
expose a boolean **`OIDCConfig.dynamically_registered`** field. It is
`true` for clients that were created through `POST /oidc/v1/register`
and `false` for everything else (legacy console-created applications,
admin-imported clients, etc.).

```ts
// Console: filter the Applications listing for DCR-registered clients.
const dcrClients = (await mgmt.listApps(projectId, 100, 0)).resultList.filter(
  (app) => app.oidcConfig?.dynamicallyRegistered === true,
);
```

The console's [Dynamic Clients view](/guides/manage/console/dynamic-client-registration#dynamic-clients-view)
uses this field to populate the listing. External tooling that wants
to display DCR-registered clients separately from operator-managed ones
can do the same.

## Client retention janitor

ZITADEL ships an opt-in periodic reaper that deletes inactive
DCR-registered clients. cavekit-dcr-bootstrap-validation.md R12.

### Why operators eventually need this

MCP clients (Claude Code, VS Code MCP, etc.) re-register on every
startup — most don't cache `client_id`, and even when they do, lost-state
scenarios force a re-register. Without cleanup, `projections.apps7` +
`apps7_oidc_configs` accumulate tens of thousands of stale clients per
year per project.

### Activity tracking

Every successful OIDC client lookup updates
`projections.apps7_oidc_configs.last_seen_at`:

- `/authorize` (auth-request creation, v1 login + v2 token endpoints)
- `/token` (every grant: authorization_code, refresh_token, jwt_profile,
  token_exchange)
- `/userinfo`, `/introspect`

Writes are throttled to once per minute per `(instance_id, app_id)` so
a busy CLI hitting `/introspect` on every command does not amplify into
projection-table churn. The throttle is process-local; the worst case
across replicas is a few duplicate UPDATEs per minute, absorbed by the
per-row idempotent UPDATE.

### Reap query semantics

A client is a reap candidate when it is DCR-registered (the eventstore-
canonical predicate is `registration_access_token_hash IS NOT NULL`)
AND one of:

- `last_seen_at < (now - MaxIdleDuration)` — last successful client use
  is older than the retention window.
- `last_seen_at IS NULL AND creation_date < (now - MaxIdleDuration)` —
  row was created before this feature shipped, OR has never had a
  successful use, AND the row's own creation has aged past the
  threshold. Freshly-registered, never-used clients are NOT reaped
  before the window expires.

Reaping invokes the same `commands.DeleteRegisteredClient` path RFC 7592
DELETE uses — events emitted, sessions revoked, projection chain
consistent.

### Configuration

```yaml
OIDC:
  DCR:
    ClientRetention:
      Enabled: false # opt-in — destructive
      Interval: 6h # tick cadence
      MaxIdleDuration: 720h # 30 days
      BatchLimit: 100 # candidates reaped per tick
```

Env-var bindings: `ZITADEL_OIDC_DCR_CLIENTRETENTION_*`.

### Enabling: pre-flight checklist

1. **Pick the retention window.** A common starting point is 30 days
   (`720h`). Tighter windows (e.g. 7 days) reduce table size faster but
   force more re-registrations from clients that genuinely run weekly.
2. **Inspect candidate count first.** Before flipping `Enabled: true`,
   run a dry-run query against the database:

   ```sql
   SELECT COUNT(*)
   FROM projections.apps7 a
   JOIN projections.apps7_oidc_configs c
     ON a.instance_id = c.instance_id AND a.id = c.app_id
   WHERE c.registration_access_token_hash IS NOT NULL
     AND (
       c.last_seen_at < NOW() - INTERVAL '30 days'
       OR (c.last_seen_at IS NULL AND a.creation_date < NOW() - INTERVAL '30 days')
     );
   ```

   If the count is in the millions, lower the `Interval` or raise
   `BatchLimit` to ensure progress; the per-tick deadline is
   `Interval/2`.
3. **Confirm metric scrape.** The two OTel metrics
   (`zitadel.dcr.client_janitor_reaped_total{result}`,
   `zitadel.dcr.client_janitor_duration_seconds`) appear once the first
   tick completes. Operators with no observability stack should
   nevertheless tail `INFO`-level logs for `dcr: client janitor reaped
   inactive clients` lines.
4. **Roll out off-peak.** The first reap tick can delete a large
   accumulated backlog. Schedule the enablement during a low-traffic
   window so the eventstore commit pressure does not coincide with
   peak registration / token traffic.

### What reaping costs the user

A reaped client is **not recoverable** — the next request from a CLI
that still has the cached `client_id` will fail with
`Errors.App.NotFound`. The CLI then re-registers from scratch (which is
fine for stateless MCP-style integrations). For long-lived clients
where the consumer expects stable identity (e.g. a CI pipeline that
caches and reuses `client_id`), pick a longer `MaxIdleDuration` or
disable the janitor.

### Disabling

Set `OIDC.DCR.ClientRetention.Enabled: false` (or unset
`ZITADEL_OIDC_DCR_CLIENTRETENTION_ENABLED`) and restart. The goroutine
exits cleanly within one tick of the process shutdown signal — no
in-flight DELETE state leaks.

## Operator hardening (defaults you don't have to think about)

The console-side IAT admin and Dynamic Clients view ship a few
hardening defaults so operators don't have to reason about them:

- **IAT plaintext is shown EXACTLY ONCE.** The "Token issued" modal
  uses `disableClose: true`, hides the token behind a Reveal click,
  auto-masks after 60 seconds, zeroes the in-memory token reference on
  close, and never returns the plaintext via `MatDialogRef.afterClosed()`.
  See R2 of the kit for the structural contract.
- **Lifetime input capped at 8760 hours (one year).** Both the form
  validator and the HTML input enforce this.
- **IAT list paginates** with default page size 100, options 25/50/100/250,
  and surfaces the total count from `ListInitialAccessTokensResponse.details.totalResult`.
- **Revoke refuses falsy `project_id`.** A toast surfaces the
  client-enforced invariant rather than dispatching a malformed request.
- **Cross-tenant abuse is rejected server-side**: an IAT scoped to
  instance/org/project A cannot register a client into B even if the
  request is routed via B's host. `dcr_iat_test.go` pins the contract.

## Upgrade note

DCR ships disabled. Existing deployments take no action on upgrade.
Operators that want to enable DCR should:

1. Confirm the deployment runs on a hostname-root issuer (no path prefix).
2. Decide between anonymous mode and IAT-required mode.
3. In anonymous mode, set `DefaultProjectID` and `DefaultOrgID` (startup
   refuses to boot otherwise).
4. Set `Enabled: true` in `OIDC.DCR`.
5. Enable the `dynamic_client_registration` instance feature flag.
6. (Optional) Mint an Initial Access Token via the admin gRPC for IAT-only
   provisioning systems.

Existing applications are unaffected by the flag flip in either direction;
the schema columns added by DCR are nullable and never block the
existing OIDC paths.

## Using with Claude Code (MCP)

Claude Code uses MCP — the Model Context Protocol — to talk to OAuth-fronted
servers. With DCR enabled, Claude Code registers itself as a public
authorization-code + PKCE client without any operator intervention:

```bash
claude mcp add my-zitadel-tool \
  --transport http \
  https://example.zitadel.cloud/mcp/my-tool
```

Claude Code then:

1. Hits `/.well-known/openid-configuration` to discover
   `registration_endpoint`.
2. Issues `POST /oidc/v1/register` with `redirect_uris=["http://localhost:<port>/cb"]`,
   `application_type=native`, `token_endpoint_auth_method=none`,
   `grant_types=["authorization_code","refresh_token"]`.
3. Receives 201 with `client_id` + `registration_access_token` (no
   `client_secret` because the auth method is `none`).
4. Drives the standard authorization-code flow with PKCE S256.
5. Persists the `registration_access_token` for any future RFC 7592
   management calls.

ZITADEL's anonymous-mode hardening (PKCE S256 enforcement, redirect URI
clamping, audit log) applies to every Claude Code registration.

For the full integration walkthrough, see the
[Claude Code MCP guide](../../guides/integrate/tools/claude-code-mcp).
